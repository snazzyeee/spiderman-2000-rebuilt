# Production pipeline, quality gates, and reference process

## What framework and production structure should a small team follow?

### Takeaway
Updated user context: solo developer with substantial programming knowledge, no game-development experience, no budget or fixed timeline; final target is the complete original game with faithful gameplay and levels, plus modern visuals. Windows PC is the canonical reference, keyboard/mouse first, eventual public release and later open source. Recommendation: retain the full-game target, build a bounded level-based vertical slice as the first milestone, keep reference research separate from authored implementation, and favor maintainable conventional code over a large framework.

Confirmed first development/performance reference machine: AMD Ryzen 5 5500, Radeon RX 580 8GB **2048SP variant**, 16GB DDR4-3000, 512GB NVMe SSD. Proposed starting test target: 1920×1080 at 60 FPS with a chosen quality preset and documented upscaling/dynamic-resolution settings. This is provisional until a representative built slice is profiled; this PC is not an established minimum specification. Record the exact GPU variant in captures rather than substituting benchmarks for a different RX 580 configuration. Keep imported/generated/build caches out of Git and monitor free SSD space as content grows.

### Cited Findings
- Unity supports batch-mode execution of a named build method, so local scripted builds can precede a CI service. — [Unity command-line arguments](https://docs.unity3d.com/6000.0/Documentation/Manual/EditorCommandLineArguments.html)
- Git LFS stores pointers in Git and actual large-file data elsewhere. Collaborators need LFS installed to obtain binary content rather than pointer files. — [GitHub LFS](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage); [GitHub collaboration](https://docs.github.com/en/repositories/working-with-files/managing-large-files/collaboration-with-git-large-file-storage)
- Unity Input System has runtime rebinding operations and binding overrides that can be saved/restored as JSON. Input package capabilities supply the input substrate, not the game's responsiveness tuning. — [Unity Input binding](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.14/manual/ActionBindings.html)
- ScriptableObjects store shared authored data as project assets; they do not provide a deployed game's player-save mechanism. — [Unity ScriptableObject](https://docs.unity3d.com/6000.0/Documentation/Manual/class-ScriptableObject.html)
- Addressables provides asynchronous asset loading; lifetime/release management remains the application's responsibility. — [Unity asynchronous loading](https://docs.unity3d.com/Packages/com.unity.addressables@2.9/manual/load-manage-asynchronous-loads.html)

### Inferences
- Proposed stack if Unity is chosen: pinned Unity 6 supported LTS selected by engine researcher, URP, C#, Input System, Cinemachine with custom wall/ceiling/camera behavior, Animator/Animation Rigging as needed, Blender, Git plus LFS. Put tunables and mission definitions in ScriptableObjects, mutable gameplay state in runtime objects, and saves in versioned data-transfer schemas. Begin with scene loading; add Addressables at a clear asset-lifetime requirement, not because the full-game goal mandates it. These are recommendations, not Unity requirements.
- Keep modules practical: Core (IDs, tags, events, clock), Player (input/controller/camera), Traversal (state arbitration, queries, movement), Combat (hit detection/damage/action state), AI, Missions (objective graph/checkpoint rules), Persistence (versioned schemas), Presentation (animation/audio/VFX/UI), DebugTests. Start with folders inside one runtime module; split into real modules/plugins when dependency or build needs justify it.
- Dependency rule: gameplay owns authoritative state; animation/VFX/UI observe events and state. Movement owns the capsule/velocity; camera reads movement targets and surface frame. Do not let independent animation, swing, crawl and combat scripts all move the player. Use explicit transition rules for ground/air/swing/wall/ceiling/ledge, with combat and stun permissions layered deliberately.
- Folder proposal:
  - `Game/Assets/_Game/Scripts/{Core,Player,Traversal,Combat,AI,Missions,Persistence,Presentation}`
  - `Game/Assets/_Game/Tests/{EditMode,PlayMode}`, `Game/Assets/_Game/{Characters,Environment,Animation,Audio,FX,UI,Data,Prefabs}`
  - `Game/Assets/_Game/Scenes/{Bootstrap,FrontEnd,Test,VerticalSlice,Missions}`
  - `Game/Assets/ThirdParty/`, `Game/Packages/{manifest.json,packages-lock.json}`, `Game/ProjectSettings/`
  - `Tools/{Reference,Import,Build}`, `Tests/{Routes,Scenarios,Fixtures}`, `Docs/{Design,Architecture,Measurements,Decisions}`, `ArtSource/`, `Licenses/`, `BuildScripts/`
  - External local-only storage (outside distributable project/repository): original executable/disc images, extracted original content, personal captures. Track only permitted authored research/specs and manifests, not original copyrighted files.
- Each new asset should have a provenance record: asset ID, creator/source URL, license/permission, original source file, processing steps, import settings, intended distribution status. CI should reject unapproved/reference-only imports from shipping manifests. This is an engineering boundary, not a guarantee of legal clearance.
- Solo build gate minimum: clean checkout + LFS fetch; verify engine/package versions; compile; run EditMode tests; run core PlayMode tests; validate scene/prefab references; build Win64; launch packaged smoke scenario; retain logs, crash artifacts, performance capture and build commit ID. Later automation adds traversal routes, mission/checkpoint scenarios and longer memory/performance runs. A local build script is enough before hosted CI exists. Keep `.meta` files with their assets and exclude generated `Library`, `Temp`, `Logs`, `obj` and build output from source control (recommended Unity workflow).
- Use modest mission maps/chunks and explicit load boundaries first. A modern open-world city, multiplayer and custom engine would enlarge scope; they are not implied by recreating a level-based game. Treat level layout, enemy counts and collectibles as authored mission data so a chapter can be reconstructed and tested independently.

### Gaps
- Available weekly time, final quality preset and proven minimum hardware remain unknown. The exact first reference PC and provisional 1080p60 target are recorded above; target feasibility still needs a representative slice. User confirmed Windows PC baseline, keyboard/mouse first and eventual public/open-source release, solo work, strong programming, zero game-dev experience, no budget and no timeline.
- Favor a cohesive modern comic/stylized art target with readable silhouettes, refined materials/lighting and new animation. Do not equate modern with photorealistic AAA assets; solo art/animation throughput is a major feasibility constraint. Full-game coverage remains the destination.

## How should the original executable and game files inform a new implementation?

### Takeaway
Yes, a legitimately obtained copy helps later as a behavioral and content-format reference; source code is not necessary to start architecture or the first mechanics prototype. First identify the exact platform, region, executable/build and patch version to avoid mixing incompatible baselines.

### Cited Findings
- Owning a physical/digital copy should not be treated as a blanket right to publish its assets or a remake. As one authoritative jurisdiction-specific example, US law distinguishes ownership of a material copy from copyright ownership; this is not a legal conclusion about the user's jurisdiction or project. — [17 USC 202](https://www.govinfo.gov/content/pkg/USCODE-2024-title17/html/USCODE-2024-title17-chap2-sec202.htm)

### Inferences
- The candidate reverse-engineering repository is now confirmed as `https://github.com/morluto/rea.git`; its detailed evaluation is assigned elsewhere. Windows PC baseline and eventual public release are confirmed. Still need exact PC edition/region/patch version and whether a copy is available. Later inspect a local file inventory and executable hashes; do not request a large upload or source code now. Game files may reveal meshes, textures, animations, sound, scripting and collision formats, but none of these are assumed until inspected. A binary is not editable original source, and recovered pseudocode still requires validation/reimplementation.
- Build a reference manifest: platform, region, patch/version, executable SHA-256, rendering/input settings, controller, measurement method, evidence timestamps and confidence. Keep observations separate from intentional improvements, with a per-feature fidelity decision (preserve/change/defer).
- Black-box measurement protocol: record reproducible actions from known starting states and collect multiple trials. Note video frame rate, game output rate and capture delay; video timings are estimates and cannot independently establish internal simulation rates. Measurements: movement speed/acceleration/deceleration in calibrated scene units; jump airtime/apex/range; air steering; swing attach/release rules and speed; wall/ceiling attachment normals and corner cases; attack startup/active/recovery and cancel windows; camera distance/yaw/obstruction/recenter; enemy detection/hit reactions; mission triggers/checkpoint restoration.
- Keep a `mechanics_spec` record with feature, setup, input sequence, observed outputs, media timestamp, confidence, original quirk, intended modern change and acceptance scenario. Record exact evidence for uncertain behavior rather than inventing it.
- Responsive controls need an input-to-action command layer, configurable buffers/forgiveness/coyote time where appropriate, controlled cancel windows, dead zones/curves, rebinding and persistent settings. A modernization mode can improve these without pretending to match original timing. Test against both gamepad and keyboard/mouse; camera accessibility needs sensitivity, invert options, camera shake and motion-blur controls, and predictable combat/traversal handoff.
- Do not commit to original geometry scale or copy original collision directly. First establish player capsule, traversal clearances, reachability and camera needs, then reconstruct layouts around chosen movement metrics. Modern physically constrained web anchors may change which original gaps are traversable; use an explicit arcade versus physical swing decision before mission art.
- Rights diligence should be a project-scope decision early: private prototype and intended public remake have different practical exposure, but neither should be represented as automatically authorized. Prefer new/approved art and audio in distributable tests. Ownership, free distribution and requiring the original game are not blanket clearance strategies.

### Gaps
- Which PC edition/region/patch version is the baseline? Full original-game coverage is confirmed, but completion criteria still need inventory of missions, bosses, cutscenes, collectibles, costumes and optional modes. The REA repository is confirmed and under separate investigation.
- Need user's location and intended release if they want legal advice; avoid expanding into unsupported jurisdiction-specific reverse-engineering claims.

## What milestones and test gates make the quality goals credible?

### Takeaway
Replace an absolute promise of bug-free/no-spike behavior with explicit release gates on named hardware and a tested scenario matrix. Use greybox mechanics and packaged-build profiling before expensive art, then prove one complete mission loop before expanding content.

### Cited Findings
- Unity Test Framework supports EditMode, PlayMode and target-platform tests, using NUnit plus Unity-specific frame/application-loop integration. Tests can run in editor, from command line, or in code. — [Unity Testing](https://docs.unity3d.com/6000.2/Documentation/Manual/test-framework/test-framework-introduction.html)
- Unity Profiler can connect to the intended release platform, as well as profile editor resource allocation. This supports verifying actual builds rather than relying solely on editor impressions. — [Unity Profiler](https://docs.unity3d.com/6000.0/Documentation/Manual/Profiler.html)
- Unity's URP documentation identifies profiling tools and performance factors, so the render pipeline must be measured under the chosen lighting/rendering configuration rather than assumed fast because it is URP. — [Unity URP performance](https://docs.unity3d.com/6000.0/Documentation/Manual/graphics-performance-and-profiling-in-urp.html)

### Inferences
- Gate 0 — decisions/reference: agree target hardware/resolution/FPS, one platform/version baseline, visual target and release scope; create mechanics evidence table, risk list, provenance policy and reproducible build instructions. Exit: no ambiguity over first slice's definition.
- Gate 1 — greybox traversal laboratory: run, jump, swing attach/release, wall/ceiling crawl, ledges, camera collisions, recoverable falls and both input devices. Include stairs, slopes, corners, narrow spaces and moving/invalid anchors. Exit: named routes pass, no camera losing the player, no blocked core transitions, movement feels acceptable to user in a packaged build.
- Gate 2 — combat/mission loop: one enemy archetype, one combat encounter, objective start/complete/fail, interaction/collectible, checkpoint, death/retry, pause/settings and exit. Exit: finish and retry the encounter reliably; no soft locks or double damage; save/reload reconstructs expected stable state.
- Gate 3 — visual/performance slice: one compact mission section at chosen art quality, audio/UI/animation/VFX, loading/streaming and first-run shader preparation. Exit: packaged route passes the agreed CPU/GPU/memory/frame-time gates under cold and warm conditions, not only in editor.
- Gate 4 — content production: only after the slice works, add mission/AI/boss variants with the same data-driven authoring and tests. Exit for each mission: objective graph complete, valid checkpoint restore, reachable goals, bounded enemy cost, no missing/cross-reference assets, tested performance route.
- Candidate quality contract (proposal, not a guarantee): zero known crash, save corruption, progression blocker or repeatable traversal soft-lock issues at release; all critical scenarios pass. For a 60 FPS target the total frame budget is 16.67 ms; establish P95/P99 and hitch counts on named CPU/GPU/RAM/storage/resolution/settings. Set thresholds with headroom using representative routes and label intentional load screens separately. Do not report only average FPS, nor promise zero OS/driver-related spikes.
- Test matrix: traversal state pairs and conflicting commands (jump/attach/attack/stun/death); surface-normal/corner transitions; high velocity thin obstacles; camera obstruction/recenter/lock-on/manual overrides; attack hitbox timing, one-hit-per-swing accounting, invulnerability, interruptions, enemy death; mission events arriving twice/out of order; save version migration, interrupted/invalid save and checkpoint retry; asset streaming at maximum traversal speed; cold start versus warm start; input remap conflicts, disconnect/reconnect, device hot-swap, focus loss, pause and frame-rate variation.
- Performance route instrumentation: log build/version, hardware/driver/config, seed, timestamped input commands, transforms/state changes/objective events, frame times and memory samples; retain a trace when limits fail. An input recording is useful for reproducing bugs, but do not assume bit-identical physics across frame rates, engine versions or hardware. Use scenario assertions/tolerances plus state snapshots; adopt fixed-step deterministic simulation only where deliberately engineered and validated.
- Measure both input simulation response and visible feedback. Input-to-photon needs external capture/measurement; the engine can log command-to-state latency but that does not measure display latency. Make time-dependent behavior robust across tested frame rates rather than tying combo or traversal windows to rendered-frame counts.
- Avoid scope traps: full-world art before movement, a custom engine, premature multiplayer/network architecture, gameplay driven by cinematic root motion everywhere, one giant Blueprint, assuming Nanite/Lumen or more hardware cures frame pacing, or integrating a large third-party framework without a small working proof. These are proposed risk controls rather than documented engine restrictions.

### Gaps
- Numeric performance targets beyond 16.67 ms for a hypothetical 60 FPS have not been agreed, and no prototype exists to establish feasible percentile/hitch/memory/loading targets. Original accuracy, visual fidelity and responsiveness may conflict; the user must rank them.
- No responsible timeline can be assigned without team/budget/hardware/scope. Propose milestone exit criteria now and estimate after the greybox/slice demonstrates real production throughput.
